# 성능·데이터 정합성 점검 기록 (2026-09-02)

원본(`Sound_Search_program`) 대비 PoC 의 인덱싱 속도 / 앱 반응성 / 데이터 정합성을
전부 **실측**으로 검증하고 고친 기록. 추측한 값은 없다.

측정 환경: 실제 `%LOCALAPPDATA%\SoundField\index.db` — **16.7 GB / 1,582,085 행**,
테스트 폴더 `D:\Soundlibrary\10.Japan_Library\JP\180329` (오디오 3,200개 / 1.42 GB).

---

## 1. 인덱싱 속도 — 엔진은 느리지 않다

PoC 는 원본 `LibraryManager` 를 **그대로 import** 해서 쓴다. 같은 폴더/같은 임시 store
로 원본 엔진 직접 호출과 PoC 브리지 호출을 비교했다 (작업량 동일: 스캔 3,200 / 신규 50).

| 구간 | 원본 엔진 직접 | PoC 브리지 | 차이 |
|---|---|---|---|
| 1단계 (파일 목록) | 0.30초 | 1.30초 | +1.0초 (고정) |
| 2단계 메타 (OS 캐시 웜) | 0.41초 | 1.31초 | +0.9초 (고정) |
| 2단계 메타 (콜드, 실제 첫 인덱싱) | — | 22.7초 | 디스크 I/O 지배 |

- 차이는 **행 수에 비례하지 않는 고정 ~1초** = 브리지 프로세스 부팅(python 시작 +
  `app.*` import + `LibraryManager` 생성). 파일이 많아질수록 비중은 0 에 가깝다.
- 콜드 22.7초는 1.42 GB 헤더를 D: 에서 읽는 비용으로, 원본도 같다.
- `scan_threads` 기본값 32 도 동일하다 (`library_manager.py:122`).

### 개선 적용
- **prewarm 을 임계 경로에서 뺐다.** `sf_admin` 은 시작 시 `app.ui.player_widget`
  (→ numpy/PyQt, 실측 0.89초) 을 **동기로** 올려서, 그 모듈이 필요 없는 첫 요청
  (보통 인덱싱)이 0.89초를 그냥 기다렸다. 백그라운드 스레드로 옮기고, 실제로 필요한
  작업(완전 제거)만 `wait_prewarm()` 으로 기다린다.
- **2단계 후 WAL 체크포인트.** 원본은 `update_index` 의 finally 에서만 checkpoint 한다
  (`library_manager.py:414`). 2단계(`update_metadata_background`)는 대량 UPDATE 인데도
  그 경로를 지나지 않아 WAL 이 계속 커진다 — 커진 WAL 은 새 연결의 첫 접근을 수 초
  지연시킨다(원본 주석이 명시). PoC 는 2단계 완료 후에도 걷어낸다.

## 2. 앱 반응성 — 검색이 매 타이핑마다 프로세스를 띄우고 있었다

가장 큰 원인. `sf_query.py` 가 **요청마다 새 python 프로세스**였다.

| 검색 1회 | 시간 |
|---|---|
| 일회성 프로세스 (기존) | **315ms** (5회 평균, 편차 ±10ms) |
| 상주 프로세스 | 23ms |
| 상주 + 읽기 연결 유지 | **2.8ms** |

- 연결을 유지하는 이유: 원본 `Database._connect` 는 **호출마다 새 연결**을 만든다
  (스레드 안전). 연결별 128MB 페이지 캐시가 매번 버려진다 — 질의 5종 평균으로
  새 연결 26.9ms vs 유지 2.8ms (**9.6배**).
- 원본은 **읽기 전용 연결에 mmap 을 걸지 않는다** (쓰기 분기에만 있다,
  `database.py:322`). 읽기 측에 걸면 FTS 검색이 **162.9ms → 28.3ms (5.8배)**.
  읽기 매핑은 쓰기 경합과 무관해 안전하다. Rust 읽기 연결에도 함께 넣었다.

### 상주 검색 프로토콜
요청 `{"id":N, ...}` 한 줄 → 응답 `{"id":N,"rows":[...]}` 한 줄. 파이썬은 **받은
순서대로** 응답한다(취소된 요청도 `{"aborted":true}` 로 응답) → 호출자는 자기 id 가
나올 때까지 줄을 읽으면 되고 순서가 어긋나지 않는다.

- 타이핑 중 밀린 요청은 **실행 자체를 건너뛴다**. 실측: 5개 연속 전송 →
  4개 즉시 취소 + 최신 1개만 계산, **전체 10.0ms**.
- 이미 실행 중인 질의는 `set_progress_handler` 로 중단시킨다.
- ⚠ 오래 사는 읽기 연결은 `wal_checkpoint(TRUNCATE)` 를 막는다 → **15초 유휴면 연결을
  닫는다.** 다시 여는 비용은 5~13ms.
- ⚠ 리더는 `os.read(0, ...)`. `for line in sys.stdin` 은 블로킹 중 TextIOWrapper 락을
  잡아 다른 스레드의 import 를 멈춘다 (관리 브리지에서 실측 0.89초 → 55초).

### ⚠ 포장 브리지(sf_bridge.exe)를 반드시 다시 빌드할 것

릴리스 빌드는 시스템 python 이 아니라 **PyInstaller 로 얼린 `sf_bridge.exe`** 를 쓴다
(`resource_dir/bridge/`). 파이썬 파일을 고쳐도 그 exe 안의 사본은 그대로다 —
이번에도 릴리스가 **개선 전 스크립트**를 물고 있었다(브리지 16:20 / 수정 21~22시).
상주 검색은 프로토콜이 바뀌었으므로 옛 브리지로는 검색이 응답하지 않는다.

    powershell -ExecutionPolicy Bypass -File .\build_bridge.ps1
    robocopy src-tauri\bridge-dist\sf_bridge src-tauri\target\release\bridge /MIR

포장 브리지 검증 (실측): query 첫 요청 270ms → 이후 **10ms**, id 순서 1·2·3 정상,
stdin 닫힘에 자체 종료 정상. admin `hide_paths []` 1,792ms 성공.

첫 검색이 프로세스 시작 비용을 다 내지 않도록 **시작 시 검색 브리지를 미리 띄운다**
(setup 에서 120ms 뒤 spawn). 실측: 첫 검색 1,997ms → **1,292ms**, 이후 한 자리 ms.
남은 1.3초는 얼린 파이썬의 `app.database` import 비용이고, 트리/카운트 스캔(3~4초)과
겹쳐 돌아 시작 총시간은 늘지 않는다.

`SEARCH {ms} rows={n}` 로그가 검색마다 한 줄 남는다 (회귀 감시 겸 QA 계측).

### 시작 구간 (릴리스 빌드)

| 구간 | 개선 전 | 개선 후 |
|---|---|---|
| 창 표시(첫 페인트 완료) | — | **166ms** |
| 루트 카운트 ROOTS | 6,528ms | **2,871ms** |
| 폴더 트리 TREE | 10,406ms | **3,926ms** |

무엇이 얼마나 기여했는지:
- **루트 카운트 1회 스캔.** 원본은 `count_files_under` 와
  `count_metadata_status_under` 를 따로 호출해 같은 LIKE 조건으로 158만 행을 **두 번**
  훑는다. 세 숫자 모두 "보이는 행" 기준이라 한 번의 스캔으로 동일하게 얻는다 —
  실측 **1,494ms → 723ms** (값 완전 동일, 플랜은 `idx_file_path_nc` 범위 검색).
- **동시 중복 조회 합치기.** 시작 직후 서로 다른 경로에서 같은 무거운 조회가 겹쳐
  들어와 ROOTS 스캔이 두 번 돌았다(로그로 확인). 진행 중인 같은 조회가 있으면 그
  약속을 공유한다 → ROOTS-IN 1회, 4.0초 → 2.99초.
- **릴리스 빌드.** 디버그 빌드는 이 경로들이 2~3배 느리다. 트리는 SQL 스캔 자체가
  1.86초(4열 158만 행, 파이썬으로 잰 하한)이고 나머지가 Rust 처리다.
- **트리 루프 무할당화** (행당 10여 회 → 새 폴더 3만 회): 디버그에서 10,406 → 10,049ms.
  기대보다 작았다 — 이 구간의 병목은 할당이 아니라 스캔 I/O 였다. 그래도 유지한다.
- 결과 목록 스크롤은 프레임당 1회로 병합 (5,000행 가상 목록의 리렌더 중복 제거).

### 손대지 않기로 한 것
- **재생 위치 이벤트(약 38회/초 → React 상태 갱신).** ref + rAF 로 바꾸면 리렌더가
  줄지만, 재생헤드 타이밍은 여러 차례 실측으로 맞춰 확정한 부분이라 회귀 위험이
  이득보다 크다.
- **폴더 트리 영구 캐시.** 원본도 세션 내 메모리 캐시(`_folders_cache`)만 쓴다.
  디스크 캐시는 정합성 정책을 새로 만들어야 해서 임의로 도입하지 않는다.

## 3. 데이터 정합성 — 원본 대비 결함 5건

검수 기준은 `docs/ai_memory/feedback_db_review_checklist.md` 의 3종 세트:
① 합성 정확성 ② 실 DB 플랜/시간 ③ 중단 잔여상태.

### F1. 라이브러리 표시 순서가 원본과 다르게 저장됐다
원본 `reorder_library_roots` 는 넘어온 목록으로 앞쪽을 정하고 **목록에 없는 나머지
루트까지** 현재 순서 뒤에 이어 붙여 `0..N-1` 을 **전부 다시 매긴다**. PoC 는 넘어온
것만 `0..k-1` 로 덮어써서, 빠진 루트가 옛 번호를 들고 있으면 번호가 겹치고 2차 정렬
(path)에 밀려 순서가 뒤섞였다. 새 루트는 `sort_order` 가 NULL 이라 특히 어긋난다.

- 검수: 루트 4개의 부분집합 순열 **40가지 전수 비교** — 새 구현은 40/40 원본과 일치,
  예전 구현은 **25건 불일치**(예: `[B]` 만 끌면 원본 `B,A,C,D` / 예전 `A,B,C,D`).
- 플랜/시간: `library_roots` 4행, 0.04ms. 단일 트랜잭션 → 중단되면 전부 무효(안전).

### F2. 블랙리스트가 대소문자만 다른 중복을 허용했다
`blacklist_paths.path` 는 `TEXT PRIMARY KEY` = **대소문자 구분**이다. `ON CONFLICT` 만
믿으면 `D:\Lib` 와 `d:\lib` 가 두 줄로 들어간다. 원본은 넣기 전에 `path.lower()` 집합
으로 걸러낸다(`blacklist_panel.add_paths:197`). 같은 판정을 SQL(`COLLATE NOCASE`)로 옮겼다.

- 검수: 합성 DB — 예전 2행 / 새 1행(설명만 갱신). 플랜은 커버링 인덱스 스캔이고
  테이블이 수십 행이라 무해. 단일 문장 → 중단 잔여상태 없음.

### F3. dup_orphan(중복 아님·미복원) 태그 해제가 DB 에 반영되지 않았다
원본 `verify_dup_orphans` 는 쌍둥이가 돌아온 행의 태그를 **DB 에서 내린다**
(`UPDATE audio_files SET dup_orphan = 0`). PoC 는 화면에서만 내려서, 목록을 열 때마다
같은 프로브를 다시 하고 다른 화면(중복 검수)에서는 계속 "중복 아님" 으로 보였다.
읽기 전용 연결이라 쓰기 연결로 따로 반영하게 고쳤다.

- 플랜/시간: 500건 `file_path IN (...)` → `COVERING INDEX (file_path=?)`, **4.9ms**
  (풀스캔 없음). 500개 단위 청크가 부분만 적용돼도 태그는 열 때 재계산되므로 무해.

### F4. 중복 검수 그룹 정렬 기준이 달랐다
원본은 **사본 개수 내림차순**이 1차, 파일명 오름차순이 2차다
(`database.py:1483`, 독스트링에도 명시). PoC 는 파일명만 기준이라, 상한(limit)에서
잘릴 때 **검수 대상 그룹 집합 자체가 달라졌다** — 원본은 사본이 많은 그룹부터 보여준다.

### F5. 종료 시 인덱싱을 그냥 kill 했다
Phase1 은 "등록(수시 커밋) → 삭제(마지막 별도 트랜잭션)" 가 비원자적이어서, 사이에
죽으면 옛 경로와 새 경로가 함께 남는다(재스캔으로 자가 회복 — 원본 주석). 종료 시
먼저 `{"op":"cancel"}` 을 보내 스스로 정리할 틈(300ms)을 준 뒤 파이프를 닫는다.

### 문제 없음으로 확인된 것
- 인덱싱/제거/숨김/복원/재시도/삭제 경로는 모두 **원본 API 를 그대로 호출**한다
  (`manager.update_index`, `remove_root`, `purge_root`, `hide_files`, `unhide_*`,
  `reset_*`, `delete_*`). 정책이 PoC 에서 다시 구현된 곳은 위 5건이 전부였다.
- `update_index` 의 finally 체크포인트는 원본 코드를 타므로 PoC 도 그대로 얻는다.
- 관리 작업은 `sf_admin` 의 단일 워커 큐로 **직렬화**되어 동시 쓰기 자체가 없다.
- 중복 탐지(파일명+크기, 보이는 행만)의 그룹 판정은 원본과 동일했다(정렬만 달랐다).
- `Y:\[Library]` 쓰기 코드는 없다 (회사 정책).

## 실행 방법 — 반드시 이 경로로 (2026-09-03 보강)

### 앱은 `app\soundfield.exe` 하나만 실행한다
바탕화면 `SoundField PoC` 바로가기와 `run_poc.bat` 이 모두 이 파일을 가리킨다.
`target\` 밖이라 `cargo clean` 으로도 사라지지 않는다.
구성: `app\soundfield.exe` + `app\bridge\`(sf_bridge.exe + `_internal`, 251개 파일).

### ⚠ `cargo build --release` 로 만든 exe 는 개발 서버를 물고 돈다
실제로 사용자가 아침에 겪은 증상이 이것이다 — 앱 창 안에 브라우저의
**"localhost 연결을 거부했습니다"** 페이지가 떴다. 로그에 원인이 그대로 남았다:

    BOOT 앱 setup 진입
    SEARCH-WARM 169ms
    SHOWWIN 안전망 발동 (프런트 신호 없음)     ← 화면 로딩 실패

`cargo build --release` 는 `tauri-build` 의 프로덕션 컨텍스트를 만들지 않아
화면 주소가 `devUrl`(localhost:1420) 로 남는다. 포트 1420 이 닫힌 상태에서
그 exe 를 실행하면 위 화면이 나온다(exe 해시 동일 · 포트 닫힘으로 실측 확인).

**프로덕션 exe 는 반드시:**

    npx tauri build --no-bundle
    copy src-tauri	arget
elease\soundfield.exe app\soundfield.exe

(`--no-bundle` = 설치본은 만들지 않는다. 이노셋업 이관은 QA 후로 미뤄둔 상태.)
검증: 포트 1420 닫힘 상태에서 `READY 요청 완료 143ms`, 검색 응답 정상, 사이드카
audio/admin/query 정상.

### 개발 빌드를 실수로 켜도 이제 안내가 뜬다
디버그 빌드는 시작 시 1420 포트를 확인하고, 닫혀 있으면 깨진 페이지 대신
"개발 빌드는 개발 서버가 필요합니다 — 바탕화면 바로가기로 실행하세요" 안내를
띄우고 끝난다. 오늘 함정이 됐던 `target\debug\soundfield.exe` 는 삭제했다.

### 검은 화면의 원인 두 가지 (해결)
1. **창을 먼저 띄우면** WebView 첫 페인트 전까지 빈(검은) 창이 보인다. 창은
   `visible:false` 로 만들고, 폰트 로딩 + rAF 2회 + setTimeout(0) 뒤에
   **Rust(`sf_ready`)** 가 띄운다. 로그 실측: `창 이미 보임=false` → 143ms 에 표시.
   프런트 신호가 못 오면 5초 뒤 강제 표시(창이 영구히 숨는 사고 방지) — 이 안전망이
   오늘 실패를 눈에 보이게 만들어 원인 추적을 가능하게 했다.
2. **`run_poc.bat` 이 개발 서버를 기다리며 검은 콘솔을 7초** 띄웠다. 릴리스가 있으면
   그것만 실행하고 즉시 끝난다. 콘솔 없는 바탕화면 바로가기도 만들었다.

## 부록 — 시작 시간은 OS 파일 캐시에 크게 좌우된다

같은 빌드, 같은 기계에서 연속 2회 (실측):

| | 1회차 (콜드) | 2회차 (웜) |
|---|---|---|
| 폴더 트리 TREE | 13,656ms | **4,144ms** |
| 루트 카운트 ROOTS | 14,539ms | **3,032ms** |

16.7GB DB 를 읽는 구간이라 아침 첫 실행처럼 캐시가 비어 있으면 3배 이상 느리다.
본문의 개선 전/후 수치는 **둘 다 웜 상태**에서 잰 값이라 비교는 유효하다.

## 부록 — 히스토리 개수 (I04) 실측 종결

앱에서 히스토리 드로어를 연 시점의 실측 로그:

    HIST stored=98 session=3 items=100 rows=100 scrollH=2520 clientH=258

파일에 98개 + 이 세션 3개 → 상한 100개, **DOM 행 100개 전부 렌더**, 스크롤 영역
2520px / 표시 258px 로 스크롤바 정상. 목록 누락은 없다. `.history-content` 에
`min-height:0; height:100%` 를 넣어 flex 높이 전파도 막아 뒀다(Chromium 은 flex
자식의 기본 `min-height:auto` 때문에 내용보다 작게 못 줄인다).

## 4. 설치본 패키징 (2026-09-03, v2.0.0)

`soundfield_installer.iss` → `installer/SoundField_Installer_v2.0.0.exe` (49.6MB,
설치 크기 170.6MB / 253파일). 빌드 순서와 함정은 .iss 파일 머리말에 적어 두었다.

- **AppId 는 원본 1.x 와 같은 값**이라 설치되어 있던 이전 버전을 "이전 버전"으로
  인식해 **삭제 후 설치**한다. 실행 파일 이름도 원본과 같은 `SoundField.exe` 로
  넣어 기존 바로가기/작업표시줄 고정이 계속 동작한다. 설치 위치는 64비트 앱답게
  `{autopf}\SoundField`.
- **사용자 데이터는 보존된다** — 인덱스 DB·피크 캐시·히스토리·채널 배치 저장은
  `%LOCALAPPDATA%\SoundField` 에, 개인 설정은 `~/.soundfield_config.json` 에 있어
  설치 폴더 밖이다. `[UninstallDelete]` 항목을 넣지 않았다(넣지 말 것).
- WebView2 런타임이 없으면 설치 전에 사유를 알린다(없으면 창이 안 뜨고 조용히 실패).

### 독립 실행 검증 (실측)
`SOUNDFIELD_PY_ROOT` 를 **없는 경로**로 두고 포장 브리지 4종을 모두 확인했다:
query / admin / audio / waveform 정상. 즉 원본 `app.*` 모듈은 exe 안에 얼려져 있다.

**단 하나 예외가 있었다 — 바이노럴.** 원본 `locate_sidecar` (app/binaural.py:295) 의
후보 목록에 **원본 저장소 안 경로**가 들어 있어, 소스 트리가 없으면
`scsearch-monitor-fixed.exe` 를 못 찾아 "바이노럴 미설치"가 된다
(실측: 원본 루트 있음 available=True / 없음 False). `build_bridge.ps1` 에
`--add-binary "…scsearch-monitor-fixed.exe;monitor"` 를 넣어 번들에 포함시켜
해결했다(없는 루트에서도 available=True).

### 개발 PC 와 설치 PC 의 동작을 일치시킨 부분
브리지 스크립트는 `sys.path.insert(0, SOUNDFIELD_PY_ROOT)` 를 한다. 그래서
원본 소스 트리가 있는 개발 PC 에서는 **소스 쪽 `app.*` 가 먼저** 잡혀 설치 PC 와
다른 코드가 돌았다(위 바이노럴 판정이 갈린 이유). 이제 Rust 가 포장 브리지에
`SOUNDFIELD_PY_ROOT=<bridge>\_bundled`(존재하지 않는 경로)를 넘겨 **항상 번들
모듈만** 쓰게 한다.

  하나씩 떴다(시작 3개 + 재생마다 1개). 모든 자식 프로세스 spawn 에
  `CREATE_NO_WINDOW` 를 준다. 검증: 사이드카 3개 · 창 핸들 0개.
- **스플래시/중앙 로더 톤**: 청색 편향이던 램프(#202834/#141922)를 거의 무채색으로
  낮췄다(#191b1f/#101216/#08090b). 상단 하이라이트·시트·액센트 글로우 알파도 함께

## 6. 아이콘·로고 (2026-09-03)

### 앱 아이콘 — 저화질의 원인은 비정사각형이었다
기존 `icon.ico` 는 **32x31 / 48x47 / 64x62 / 128x124 / 256x249** 로 정사각형이 아니었다.
윈도우는 정사각 아이콘을 기대해 늘려 그리므로 작업 표시줄에서 흐릿하게 보인다.
`tools/make_icon.py` 로 **16·20·24·32·40·48·64·128·256 전부 정사각** 재생성한다.

디자인은 툴 로고(파형)를 현대 앱 아이콘 관례에 맞춰 올렸다 — 얇은 링+얇은 선은
16px 에서 사라지므로 **꽉 찬 라운드 타일 + 굵은 흰 글리프**로 바꿨다. 깊이는 세 가지만:
대각 3단 그라디언트 / 상단 엣지 하이라이트 / 글리프 그림자·발광.

### ⚠ 아이콘만 바꾸면 exe 에 반영되지 않는다
`icon.ico` 만 교체하고 빌드하면 cargo 가 `build.rs` 를 다시 돌리지 않아 **옛 아이콘이
남는다** (실측: 교체 후 빌드했는데 추출한 아이콘이 이전 것). `tauri.conf.json` 의
수정 시각을 갱신해 build.rs 재실행을 강제한 뒤 빌드하고,
`[System.Drawing.Icon]::ExtractAssociatedIcon(exe)` 로 눈으로 확인한다.
표시가 여전히 옛것이면 윈도우 아이콘 캐시다 — `ie4uinit.exe -show`.

### 소속 마크 — 26px 에서 읽히도록 단순화
원본 선 디자인(투명 버전.png, 2076x740)은 얇은 아치 5~6줄 + 곡선 글자가
있어 타이틀바 크기(26px)에서 뭉개졌다. 같은 구성을 SVG 로 다시 그렸다 —
좌측 상단의 꽉 찬 반원 / 우측 상단으로 뻗는 아치 커팅 4줄 / 중앙 라벨 / 아래로
좁아지는 막대 3줄, 곡선 글자는 제외. 커팅은 SVG 마스크라 실제로 뚫려 어떤 배경에서도
맞고, 색은 `currentColor` → 테마 잉크(`--sc-logo-ink`)로 제어된다
(어두운 UI 에서는 흰 선으로 반전).

스플래시는 컬러 엠블럼(`public/sc_logo.png`)을 그대로 쓴다 — 단색 반전은 툴 화면만이다.
