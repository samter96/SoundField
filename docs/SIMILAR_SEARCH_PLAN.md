# 유사 사운드 검색 (Similar Search) 설계 계획

작성 2026-09-10. 조사 + 실측 근거 포함. **미승인 계획 — 결정 대기 항목은 §7 에 모아둠.**

---

## 1. 목표

재생 중인 사운드와 비슷한 소리를 내 라이브러리(158만 파일 / 8,963시간) 안에서 찾아
유사도 순으로 정렬한다. 오프라인·로컬 동작.

## 2. 다른 도구는 어떻게 하나 (조사 결과)

| 도구 | 방식 |
|---|---|
| Soundly `Find Similar` | 로컬 라이브러리의 "음향적 특성"을 분석해 오프라인에서 유사 파일 검색. 내부 알고리즘 비공개 |
| Sononym | 유사도를 **5개 축**으로 분리 — Overall / Spectrum(주파수의 시간 변화) / Timbre(음색) / Pitch / Amplitude(음량 프로파일). 축별 가중치를 사용자가 조절하고, 축별 점수의 평균을 최종 유사도로 정렬 |
| Freesound | Essentia + AudioCommons 기술자(스펙트럴/시간/톤) 로 벡터화 후 최근접 이웃. 44.1kHz 모노 다운믹스, 프레임 2048 / 홉 1024 |
| BaseHead | 유사도 검색보다 메타데이터·즉시 검색 중심. 오디오 지문 기능은 확인되지 않음 |
| 학계 최신 | CLAP(대조학습 오디오-텍스트) 임베딩이 VGGish·PANNs 대비 검색 성능 우위. 환경음에서 VGGish 는 지각 점수와 상관 0.1 미만으로 부적합 |

**"파형을 보고 판단"에 대한 검토** — 사용자 직관은 절반 맞다. 진폭 엔벨로프(어택/감쇠)는
타격음·연속음을 가르는 **강력한 축 하나**지만 단독으로는 개 짖는 소리와 문 두드리는 소리를
구분하지 못한다. Sononym 이 Amplitude 를 5축 중 하나로만 두는 이유다. 따라서 엔벨로프는
채택하되 **음색(스펙트럼)·스펙트럼 변화**와 함께 가중 결합한다.

## 3. 이 환경의 제약 (실측)

무작위 표본 30개씩, 3초 부분 읽기 + numpy 특징 추출 중위값:

| 루트 | 파일 수 | open | read | 특징계산 | 합계 | 읽은 양 |
|---|---|---|---|---|---|---|
| `D:\Soundlibrary` (로컬) | 644,238 | 79.4ms | 3.4ms | 2.7ms | **92.1ms** | 775KB |
| `Y:\[Library]` (NAS) | 937,574 | 118.6ms | 118.3ms | 9.1ms | **257.3ms** | 1,179KB |

- **비용은 전부 I/O**다. 특징 계산은 3~9ms 로 무시 가능 — 즉 "가벼운 특징이냐 무거운 특징이냐"는
  1차 관심사가 아니고, **파일을 몇 번 여느냐**가 전부다.
- 전체 1회 통과: 총 읽기 **약 1.5TB**. 워커 32 기준 산술 추정 D: 0.5시간 + Y: 2.1시간 = **약 2.6시간**.
  단 I/O 병목이라 병렬 32배가 선형으로 나오지 않는다 — **실제로는 4~8시간, 야간 1회 작업**으로 본다.
  ([[project_phase2_bottleneck_measured]] 와 동일한 결론: open() 자체가 병목)
- 파형 피크 캐시는 재생한 파일만 있어 재활용 불가 (현재 274개 / 21MB).
- 현재 중복 검수는 (파일명, 크기) 그룹 비교로, 오디오 지문 기반이 아니다 → 재사용할 지문 인프라 없음.

## 4. 파이썬 3.14 의존성 현실

설치 확인: `numpy 2.4.4` / `soundfile` / `sounddevice` / `mutagen` **있음**,
`scipy` · `librosa` · `onnxruntime` · `torch` **없음**.
onnxruntime 은 Python 3.14 휠 요청 이슈(#26473, #26309)가 열린 채 미해결이다.

→ **딥 임베딩을 쓰려면 파이썬이 아니라 Rust 쪽 `ort` 크레이트(2.0.0-rc, ONNX Runtime 1.28 래핑)로
붙이는 게 맞다.** 앱이 이미 Tauri(Rust) 코어라 추가 런타임이 필요 없다.
반대로 1단계 DSP 특징은 **numpy 만으로 완결**된다 (FFT·멜필터뱅크·DCT 직접 구현, 실측된 그 코드).

## 5. 제안 설계

### 5.1 특징 벡터 (1단계 · numpy 전용, 87차원)

3초 구간을 16kHz 모노로 만들고 프레임 1024 / 홉 512:

| 축 | 내용 | 차원 |
|---|---|---|
| 음색 | MFCC 20 의 평균·표준편차 | 40 |
| 스펙트럼 변화 | MFCC 1차 차분의 평균·표준편차 | 40 |
| 밝기·잡음성 | 스펙트럴 센트로이드 / 플랫니스 각 평균·표준편차 | 4 |
| 엔벨로프 | 피크·평균 RMS, 피크 위치 비율(어택 성격) | 3 |

저장: float16 174B × 158만 = **약 275MB**. float32 면 550MB.
검색: 158만 × 87 행렬 곱 = 수백 ms → 브루트포스로 충분, ANN 색인 불필요.

축별 점수를 따로 보관해 **Sononym 식 가중치 조절**(음색/변화/밝기/엔벨로프 4축)을 지원한다.

### 5.2 하이브리드 순위

최종 점수 = `w1·음향유사도 + w2·메타데이터 유사도`
메타데이터 쪽은 이미 있는 자산을 그대로 쓴다 — UCS 카테고리/서브카테고리 일치,
동의어 사전(`app/data/ucs_thesaurus.json`), 키워드 교집합.
순수 음향만 쓰면 "쇠 마찰음 ↔ 새 울음" 같은 장르 이탈이 나오므로 카테고리로 눌러준다.

### 5.3 긴 파일 처리

- 60초 초과 파일 136,927개(전체의 8.7%)는 파일 1벡터로 요약하면 의미가 깨진다.
- **구현된 방식(3단계)**: 세그먼트 검출을 쓰지 않고 파일 전체에 **균등 간격 3초 창 최대 4개**를
  잡아 창마다 한 행씩 넣는다. 세그먼트 검출은 파형 캐시(재생한 파일만)에 의존해
  색인 시점에 쓸 수 없고, 창 수를 늘리는 것이 곧 I/O 비용이기 때문이다.
- 질의 쪽은 §7 대로 사용자가 팝업에서 고른 영역을 쓴다.

### 5.4 추출 시점

Phase1(파일 목록) / Phase2(메타) 에 이어 **Phase3(음향 특징)** 을 별도 단계로 둔다.
Phase2 는 mutagen 헤더만 읽어 오디오를 디코딩하지 않으므로 합칠 수 없다.
취소 즉시 응답·부분 진행 보관 등 기존 인덱싱 규칙(`CLAUDE.md`)을 그대로 따른다.

### 5.5 2단계(선택) — 딥 임베딩

1단계 품질이 부족하면 Rust `ort` + 경량 CLAP(예: DCLAP, 오디오 타워 7M 파라미터로 축소하고
512차원 유지, 5~6배 빠름)을 추가한다. 512차원 float32 는 3.2GB 라 int8 양자화 또는 PCA 축소,
검색은 hnswlib 급 ANN 이 필요하다. **주의: 1.5TB I/O 를 다시 치러야 하므로 1단계와 같은 통과에서
같이 뽑지 않으면 두 배로 든다.** 다만 멜 스펙트로그램을 캐시해두는 방식은 158만 × 6KB ≈ 10GB 라
현재 DB(7.2GB) 대비 부담이 커서 권하지 않는다.

## 6. 단계별 작업 순서 (권장)

1. 특징 추출기 모듈 (numpy 전용, 파이썬) + 단위 테스트
2. DB 스키마 — 특징 벡터 저장소 + 진행 상태 컬럼, 자동 마이그레이션
3. Phase3 배치 추출 (워커 32, 취소·재개 지원, 진행률·ETA)
4. 질의 경로 — 재생 중 구간 → 벡터 → 브루트포스 → 축별 점수 반환 (Rust 명령 + 상주 프로세스)
5. UI — "유사 사운드 찾기" 진입점, 유사도 컬럼, 축 가중치 조절
6. 귀로 검증 — 대표 카테고리(발소리/총성/문/앰비언스/UI) 표본으로 사람 평가

### 2단계 DB 스키마 — 완료 (2026-09-10)

`app/database.py` — 기존 마이그레이션 관례(`_ensure_indices`)를 그대로 따른다.

```
similarity_vectors (file_id, win, start_sec, end_sec, vec BLOB, PK(file_id,win)) WITHOUT ROWID
audio_files += sim_extracted(0 대기/1 완료/2 실패), sim_error, sim_run_id
idx_sim_pending_v2 (sim_extracted, meta_extracted, hidden, removed) WHERE sim_extracted=0  -- 커버링
idx_sim_failed_v1  (sim_extracted) WHERE sim_extracted=2
index_meta: sim_feature_version, sim_total_eligible
```

**저장 방식 실측(200만 행 기준)**: 행당 BLOB 기록 75초 / 파일 447MB / 전체 적재 2.18초.
묶음(4096개) BLOB 은 기록 35초 / 394MB / 적재 1.97초 로 차이가 작아 **단순한 행당 BLOB 채택**.
검색은 float16 상주(332MB) + 블록 변환 **213ms**, float32 전량 상주(664MB)는 21ms —
**사용자 결정: float16 상주**.

**실제 DB 사본(1,582,033행 / 7.22GB) 검수 결과**

| 항목 | 결과 |
|---|---|
| 마이그레이션 1회 | 3.43초, DB 7.22 → 7.24GB (+18MB) |
| 두 번째 오픈(멱등) | 1.12초, 추가 작업 없음 |
| 대기 목록 1000건 | **1ms** — `SEARCH ... USING INDEX idx_sim_pending_v2` |
| 진행 집계(실 API) | **102ms cold / 96ms warm** — `USING COVERING INDEX` |
| 대상 총계 1회 계산 | 896ms → 시작 시 1회만, `index_meta` 캐시 |
| 정합성 | 행 수 불변, 고아 벡터 0, `quick_check ok` |

**여기서 잡은 결함**: 처음 쓴 진행 집계(CASE SUM)는 `idx_meta_extracted` 를 타고
테이블을 다시 읽어 **1,079ms** 였다. 진행률 폴링에 쓸 수 없는 값이라
필터 4개 컬럼을 담은 커버링 부분색인으로 바꿔 86~102ms 로 내렸다.
완료 수는 세지 않고 `총계 − 대기 − 실패` 로 구한다 (총계 집계가 896ms 라 폴링 불가).

**중요한 사실 — 추출 대상은 158만이 아니라 114만이다.**
`meta_extracted=1 AND hidden=0 AND removed=0` 기준 **1,141,329개**.
중복 검수로 숨긴 44만 개가 빠지므로 §3 의 시간 추정도 그만큼 줄어든다.

검수: `python -m unittest tests.test_similarity tests.test_similarity_db` (34개 통과)

### 3단계 배치 추출기 — 완료 (2026-09-10, 표본 실행까지)

`app/similarity_indexer.py` — `SimilarityIndexer(db_path, workers=32)`.
`run(progress_cb, max_files)` 로 돌리고 `cancel()` 로 즉시 세운다.

지킨 규칙 (기존 Phase1/2 와 동일)
- 투입 루프·수집 루프 양쪽에서 `_cancel.is_set()` 확인, `as_completed` 대신 직접 확인
- `ThreadPoolExecutor` 는 `with` 금지, `shutdown(wait=False, cancel_futures=True)`
- 취소해도 **이미 계산이 끝난 창은 걷어서 저장**한다 (NAS 를 다시 읽는 것이 비용 전부)
- 취소 시 세션 분모(`sim_total_eligible`)를 지우지 않는다

**개발 중 실제로 낸 결함 1건** — 저장 배치(400개)가 찰 때까지 미루면, 그 파일들이 아직
`sim_extracted=0` 이라 다음 조회가 같은 것을 또 꺼내 **무한 루프**가 됐다.
배치 경계에서 반드시 비운다 (코드에 ⚠ 주석).

**실제 라이브러리에서 잡은 결함 2건**

1. **MP3 마지막 창 읽기 실패** — libsndfile 이 보고하는 프레임 수가 실제보다 커서
   파일 끝에 붙는 마지막 창에서 `LibsndfileError` 가 난다. 앞쪽 창들은 정상.
   무작위 D: 표본 1,000개 중 34개(3.4%), 특정 폴더는 60개 중 53개가 여기서 죽었다.
   → 창 단위로 실패를 허용하고 살아남은 창만 쓴다. **53/60 → 0/60**.
2. **DB duration 을 길이 판정에 쓰면 안 된다** — mp3 표본 150개 중 **83개(55%)** 가
   실제와 다르다(최악 DB 16.4초 vs 실제 74.2초, 4.5배). wav/aif/flac 은 150/150 정확.
   DB 값을 믿으면 62초 파일이 짧은 파일로 취급돼 한 벡터로 뭉개진다.
   → 파일에서 읽은 실제 길이(`RegionFeatures.file_sec`)로 판정한다.
   ⚠ **결과표에 보이는 길이 자체가 틀린 기존 버그**이기도 하다 — 별도 과제로 분리.

**표본 실행 결과 (실제 파일, DB 사본에만 기록)**

| 항목 | 값 |
|---|---|
| 순차 접근(추출기 실제 경로) | 3,000개 / 33.1초 = **90.6 파일/초** (전부 D:) |
| 무작위 접근 D: | 21.2 ~ 177.2 파일/초 (캐시·HDD 상태에 따라 요동) |
| 무작위 접근 Y: NAS | **9.9 ~ 16.1 파일/초** |
| 파일당 벡터 | 1.00행 (표본에 긴 파일이 44개뿐) |
| 실패 | 0 (수정 후) |
| 같은 파일의 다른 대목끼리 | 평균 유사도 **+0.717** |
| 서로 다른 파일끼리 | 평균 유사도 **+0.003** |

마지막 두 줄이 중요하다 — 같은 소리의 다른 대목은 서로 붙고, 무관한 파일은 0 근처다.
정규화·거리 계산이 의도대로 동작한다는 뜻이다.

**전수 예상 시간** — 지배 항목은 NAS 69만 개다. 무작위 접근 기준 12~19.5시간,
순차 지역성이 살면 훨씬 짧다. 정직하게 **하룻밤 규모(6~20시간)** 로 본다.
중단·재개가 되므로 조각으로 나눠 돌려도 된다.

검수: `python -m unittest tests.test_similarity tests.test_similarity_db tests.test_similarity_indexer` (48개 통과)

### 4단계 질의 경로 — 완료 (2026-09-10)

`app/similarity_search.py` — `SimilarityIndex(db_path)`.
`load()` 로 벡터를 상주시키고 `search(query_vec, ...)` 로 상위 N 을 받는다.

- **적재 시 z-정규화 + L2 정규화까지 끝낸다.** 질의마다 하면 낭비고, 원값 코사인은
  센트로이드가 독점해 쓸 수 없다. 상주분은 float16 (사용자 결정).
- **파일당 한 줄만 낸다.** 긴 파일은 대목이 여러 행이므로 가장 잘 맞는 대목만 남기고,
  그 대목의 `start_sec/end_sec` 을 같이 돌려준다 — UI 가 그 지점을 바로 들려줄 수 있다.
- **숨김·제거 파일은 후보 메타 조회로 걸러낸다.** 벡터 행은 삭제 경로에서만 지우므로
  이 필터가 없으면 숨긴 파일이 결과에 새어 나온다 (개발 중 실제로 새서 테스트로 고정).
- 순위 = `0.75 × 음향 + 0.25 × 카테고리결합`. **이 가중치는 잠정값이고 귀 튜닝 대상**이다.
  카테고리 결합은 후보 상위 3,000개만 DB 에서 메타를 읽어 재정렬하므로 비용이 거의 없다.

**실제 파일 전 과정 검증 (7,200개 말뭉치, 8 카테고리 × 900)**

| 항목 | 값 |
|---|---|
| 추출 | 7,200개 실패 0 / 440초 (16 파일/초, NAS+로컬 무작위) |
| 적재 | 7,553행 |
| 질의 시간 | 중위 **45ms** |
| 상위 5 중 같은 그룹 | **평균 72%** (무작위 기대치 12%) |
| 카테고리 결합 효과 | 71.9% → 74.4% |

그룹별: 물 100% · 발소리 96% · 총성 80% · 앰비언스 72% · 차량 64% · 폭발 60% ·
문 52% · UI 52%. 약한 쪽(문·UI)은 §9 1단계에서 본 것과 같은 이유다 —
짧은 어택·광대역이 서로 붙는다.

정직한 한계: 그룹당 질의 5개라 표본이 작다. "같은 그룹"은 파일명 낱말로 판정한 것이라
지각적 유사도의 대리 지표일 뿐이다(문 소리가 나무 충격음을 물어오면 오답으로 세지만
실제로는 좋은 결과일 수 있다). 카테고리 결합 이득 +2.5%p 는 질의 32개 기준이라
잡음 범위 안이다 — **귀로 듣고 가중치를 정해야 한다.**

검수: `python -m unittest discover -s tests -p "test_similarity*.py"` (66개 통과)

### 질의 커버리지 보강 — 완료 (2026-09-10)

사용자 지적: "전체 영역 선택이든 드래그든 3초를 넘을 텐데 3초만 듣고 판단하나?"
→ 실제로는 창 4곳(최대 12초)을 평균하고 있었고, **영역이 길어지면 커버리지가
무너지는 것이 맞았다.** 1분이면 20%, 5분이면 4% 만 듣는다.

**정규화 공간에서 재측정한 차이** (원값 코사인 0.99 는 센트로이드 독점 때문에 착시)

| 영역 길이 | 표본 vs 전체 코사인 | 상위 5 겹침 | 1등 동일 |
|---|---|---|---|
| 20~45초 | 0.971 | 78% | 67% |
| 45~90초 | 0.962 | 60% | 67% |
| 150초 이상 | 0.916 | **55%** | **67%** |

→ `app/similarity.py` 의 `features_from_region_full` 추가. 질의는
`SimilarityIndex.search_region(path, start, end)` 으로만 들어가게 묶었다
(색인용 표본 함수를 질의에 잘못 쓰는 것을 막는다).

**덩어리로 끊어 읽는다** — 창 100개를 따로 seek 하면 5분을 죽 읽는 것보다 더 느리다
(30초 파일에서 창 4개 표본 123~920ms vs 전체 읽기 77~310ms). 찾아가는 횟수를 10회로 묶었다.

**구현 후 실측 (실제 파일)**

| 영역 | 표본 4개 | 전체 듣기(D:) | 전체 듣기(Y: NAS) | 창 수 | 분석량 |
|---|---|---|---|---|---|
| 30초 | 142~180ms | 212ms | 83ms | 9 | 27초 |
| 1분 | 22~95ms | 108ms | 334ms | 19 | 57초 |
| 5분 | 263~859ms | 1.8초 | 4.2초 | 100 | 300초 |
| 20분 | 163~388ms | 1.1초 | 4.8초 | 100 | 300초 |
| 87분 | 632ms | 1.1초 | 4.4초 | 100 | 300초 |

상한이 걸려 **87분 파일도 4.4초에 끝난다** (상한 없이 다 읽으면 47초).
1분 이하는 전체를 읽는 편이 표본보다 빠른 경우도 있다.
최악은 NAS 에서 약 5초 — 버튼 한 번의 대기로는 다소 길다.

**여기서 잡은 결함**: 말뭉치가 2~3개뿐이면 정규화 통계가 병적으로 나온다.
두 파일이 거의 같은 값인 차원의 편차가 0 에 가까워져 미세한 차이가 수천 배로
증폭돼 순위를 뒤집는다. z-점수를 ±10 으로 자르고(`Z_CLIP`),
`MIN_ROWS_FOR_STATS = 50` 을 근거로 남겼다 — **추출 초반에 검색하면 순위를
믿을 수 없다**는 뜻이라 UI 에서 다뤄야 한다.
